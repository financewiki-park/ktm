# 0.1.11 구조 및 검증 검토

## 사용자에게 발생한 실패

- 0.1.7–0.1.9: 메뉴 5번 선택 시 라이브러리로 복귀.
- 0.1.10: 앱 자체가 열리지 않음.
- 이 기록은 사용자 보고이며, 실제 Kindle 프로세스 로그를 확보하지 못했으므로
  종료의 단일 원인이 특정됐다고 말할 수 없다.

## 배포 파일과 소스에서 확인한 문제

1. 0.1.9는 공식 KTerm의 메뉴 안에서 새 GTK/VTE 터미널을 시작했다.
   0.1.10은 그 자체 바이너리를 앱의 유일한 시작 경로로 바꿨다.
   검증되지 않은 GUI가 실패하면 메뉴 자체도 사용할 수 없는 구조였다.
2. 0.1.10의 `ktmterm`은 정적 실행 파일이 아니다. GTK, GLib, X11 등
   다수의 기기 라이브러리를 로드해야 한다.
   공식 KTerm과 달리 `libharfbuzz.so.0`, `libbz2.so.1.0` 의존성이 직접 들어 있다.
   이것이 사용자 기기에서 실제로 누락됐는지는 미확인이다.
3. 테스트는 Telegram helper 및 tar 내부 파일 유무만 검사했다.
   GTK 창 생성, shell 시작, 입력 전달은 테스트하지 않았다.
   `strings`에서 문구를 찾거나 컴파일이 성공한 것은 런타임 성공 증거가 아니다.
4. 0.1.10은 요청 표식을 보고 800ms를 기다려 텍스트를 넣었다.
   셸이 준비됐다는 확인 없이 입력하고, 전달 뒤 원문을 지웠다.
5. 문서가 초기 버전 상태여서 실제 배포/CLI/데이터 구조와 불일치했다.
6. 이전에는 소스 커밋이 아직 없는 새 아카이브를 인덱스에서 먼저 가리킬 수 있었다.

## 수정 설계

공식 KTerm 하나가 메뉴와 셸을 계속 표시한다.
GTK/VTE 빌드를 제거하고, `ktm-input`은 libc만 사용하는 정적 ARM 실행 파일로 만든다.
helper가 자신의 PTY와 자식 셸을 소유하므로 다른 앱의 프로세스에 입력을 주입하지 않는다.
셸 프롬프트를 읽어 준비를 확인하고 텍스트만 전달한 뒤 사용자의 키 입력을 중계한다.
실패 또는 셸 종료 시 메뉴로 돌아간다. 원문은 그대로 둔다.
KTerm 시작 오류는 `logs/startup.log`에 남긴다.

직접 입력은 한 줄 512바이트까지다.
새 메시지는 `current.txt` 한 건을 갱신하며 오래된 메모를 쌓지 않는다.
원본 제작지시서의 여러 줄 붙여넣기·범용 clipboard·한글 키보드 통합은 완성되지 않았다.
이를 기능 완료로 안내해서는 안 된다.

## 검증 범위

- 실제 PTY와 셸: 입력이 보이지만 Enter 전 실행되지 않는지 확인.
- Enter 후 UTF-8 결과 확인, Ctrl+U 편집 교체, Ctrl+C 취소.
- 빈 입력, 제어문자, 개행, 길이 초과 거부 및 원문 보존.
- 전체 session: 5번 → 입력 → Enter → exit → 같은 메뉴 복귀.
- 공식 KPM KTerm 호출 인자 및 공백이 있는 설치 경로.
- 실패 시 메뉴 복귀, 비실행권한 shell script 처리, 시작 오류 로그.
- 배포 시 BusyBox 셸 및 QEMU의 실제 ARM helper로 입력 테스트.
- manifest v2, ARM hard-float, 공유 라이브러리/동적 로더 없는 ELF 검사.

이 검증은 기기 펌웨어, 실제 GTK 화면, 한글 글꼴/키보드, 절전 동작을 재현하지 않는다.
사용자 Kindle에서 업데이트 후 앱 진입과 5번 동작이 확인돼야 실기기 해결로 판단할 수 있다.
